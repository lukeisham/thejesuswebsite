# Decisions Log

The dated record of important decisions and permissions: what was decided, when, who granted it, and why. It shows a future agent how things got that way, so that it does not undo a choice it thinks is a mistake.

This file is tracked in git (a `.gitignore` exception), so it is on GitHub and can be
recovered. It holds no secrets.

Decisions on the Wikipedia classifier's labelling rules, its labeller and its activation gate
live in `Wikipedia algorithm/Classifier_decisions.md` instead (D-056). They follow every rule in
this file. A classifier decision that also changes the site, the deploy or a permission goes
here.

## What goes in this log

### An important decision

A decision goes in this log if **any** of these is true:

1. **A future agent would undo it.** An agent that reads only the code, the guides and the rules
   would likely undo it, or do it differently (the CORE-4 test).
2. **It is hard to reverse.** It sets the database schema shape, a data migration, the URL
   structure, the public API or MCP contract, or the deploy and server setup.
3. **It adds or removes a moving part.** A dependency, a service, a pm2 process, a cron job, or
   an outside API.
4. **It changes what is safe or public.** Auth, security, privacy, or what content the public can
   see.
5. **It picks between real options.** Two or more workable designs existed, and the choice has a
   trade-off.
6. **It reverses an earlier entry.** Any change to a decision in this log is itself a decision.

These are **not** important decisions. They go in the commit message only:

- routine edits, refactors and renames;
- a bug fix that restores the intended behaviour;
- a choice that the rules or the style guide already make;
- a choice that any capable agent would make the same way.

### A permission

A permission is Luke's explicit grant to do something that a rule or a default forbids. It goes
in this log if it is **standing**, that is, it applies again in the future:

- a rule exception (CORE-4) — it lives only in this log. Its `Rule` column names the rule it
  breaks, and an agent finds it by searching this file for that rule. The exception text is not
  written into `setup/Vibe_coding_rules.md`;
- a new dependency, or a new language for a service (SR-2, PY-1);
- a standing grant to an agent, for example "agents can do X without asking".

A one-off confirmation (for example, one destructive migration under MIG-7) is not a standing
permission. Record it in that commit message.

Only Luke grants a permission. An agent can draft the entry, but only after Luke says yes in
chat. A permission that is not in this log, or not under its rule, does not exist (CORE-4).

## How to write an entry

- **One row per entry.** Each entry is one row in the `## Entries` table. The columns, in order,
  are: ID | Title | Type | Date | By | Applies to | Rule | Status | Decision | Why | Rejected |
  Where it lives.
- **Cells hold short phrases.** Escape a literal `|` as `\|`. Write `none` for a field that does not
  apply.
- **Type** is `Decision`, `Permission`, or both. **By** is `Luke`; an agent draft says
  `Luke, in chat` for a grant made in chat.
- **Append only.** Add new rows at the bottom, with the next number. Never reuse a number. Both
  logs share one `D-NNN` series: the next number is one more than the highest ID in either log.
- **Never rewrite an entry.** To change a decision, add a new row. Then change only the **Status**
  cell of the old row to `Superseded by D-NNN`.
- **Amends.** An entry that amends another says so in its Status cell (`Amends D-NNN`), and the
  amended entry's Status cell names the amendment (`Amended by D-NNN`).
- **Status** holds only this wording, so that a search for `Superseded` or `amended by` finds
  every changed entry. It starts with `Active`, `Provisional` or `Superseded by D-NNN`. `Active`
  or `Provisional` can be followed by `; amends D-NNN` or `; amended by D-NNN`. A list of IDs is
  separated by commas, and an ID can carry a short scope in brackets: `Superseded by D-033
  (blend range only)`. An open problem goes in `setup/ISSUES/Issues.md`, not in this cell.
- **Keep it short.** Give the reason and the trade-off, not a design document. Link to the plan
  or the guide for detail.
- **Dates** are the day of the decision, in Luke's time zone. If the exact day is not known,
  write `by <date>` with the date of the first commit that records it.
- **Guide test.** `api/tests/guide-decisions-log.test.js` checks the ID, Date and Status cells
  of both logs.
